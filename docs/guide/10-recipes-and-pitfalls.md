# 提示词示例与常见陷阱

下面的提示词可以直接复制。把路径和完成条件换成自己的。示例刻意用平常说话的口吻，技能可以从中读出实际意图。页面末尾列出常见错误。

![她品尝做完的菜，机器人照着食谱卡做饭。台面上方的卡片写着 /how、/tdd 和循环调度。](./images/recipes.jpg)

*上游插图中的 `/loop` 对应 AGY 的 `schedule` 工具或 `/schedule` 命令。*

## 理解不熟悉的子系统

```text
先用 /how 看懂这段初始化怎么工作，再用 /why 查它最近为何出了问题。
```

先看机制，再查历史。每个技能的报告会告诉你查了哪些来源，你可以核对结论的依据。

## 在动代码前复述线索杂乱的报告

```text
/poteto-mode 阅读这串讨论，用自己的话平实地复述根本问题。先别改代码。
```

有误解，复述时就能看出，只需一条消息就能纠正。等代理讲清自己的理解，再说你对原因的猜测。只需要复述时用 `/in-your-own-words`，无需整个 playbook。

## 发出提示词前先打磨

```text
/sharpen 为新的计费服务写一份上手文档。
```

代理会列出专家会补做的事、会使用的原始材料及具体方法和工具，还有能独立验证结果的方法。它把这些要求写进提示词交给你。看改写是否符合意图，再发送它执行。

## 先做原型再选方案

```text
/poteto-mode 为设置页布局做几个原型。用一个切换器展示各版，把每版截图发给我。
```

从能运行的方案中挑。代理也能在做原型时自行回答布局和时序问题。

## 把定下来的设计变成计划

```text
/poteto-mode 把这个设计变成计划。拆成可验证的小 PR，每个 PR 给出独立证据。
```

设计确定后再提出这个请求。交付物是计划，计划会指出用哪个 playbook 执行。

## 为设计找独立意见

```text
请 /arena 对这串讨论和我们现在的方案给一个独立意见。
```

当前设计成为多个候选之一。综合结果会说明评审面板找到了更好的办法，还是确认你的方案可行。与日后撤回难以逆转的设计相比，这一步成本较低。

## 并行检查独立分片

```text
/pstack-swarm 对 packages/ 下的每个包运行它自己的 check.sh。每包一个工作代理，给我一份报告。
```

每个工作代理负责一个包。父会话等各分片完成，汇总为一份 `PASS`、`ISSUES` 或 `BLOCKED` 报告，省去原始输出堆砌。

## 审查分支时保持怀疑

```text
/interrogate 用怀疑的态度审查整个分支。先不改任何东西。只报真实缺陷或行为回归。
```

「先不改」将范围限定为只读。只报真实缺陷的要求会先过滤吹毛求疵的意见，留下值得核查的已验证发现。

## 用失败测试修缺陷

```text
/poteto-mode 先复现重复写入。如果有低成本的测试途径，就用 /tdd。然后修复并重跑。
```

「如果有低成本的测试途径」决定流程。用脆弱的 mock 强行拼出测试，证据可能比不上真实命令。playbook 可以据此选真实命令。

## 复现并修复报告里的缺陷，附证据

```text
/poteto-mode 用 /verify-<app> 复现。如果在 main 上能复现，就修复并录一段视频作证。
```

「如果在 main 上能复现」让任务在缺陷已消失时可以提前结束。录像让你读 diff 之前就能核查修复。

## 证明测试很少触及的性质

```text
/create-formal-verification-skill 检查重试队列。任何消息都绝不能投递两次。
```

你会拿到一个在声明范围内对所有情况都检查过的性质。如果现有代码已违反它，还会拿到一条用代码术语描述的反例。生成的项目技能供下一个代理在改动相关代码时运行。

## 发出数字前先核实

```text
/benchmark-checklist 这 40% 的提速要写进 PR 描述，先核实数据。
```

结论会是更快、更慢、无可测差异或无法判定，并给出运行次数、结果范围和限制因素。

## 让同样的错误不再重复

```text
/correct 代理反复添加配置参数，却没有在 schema 中注册。
```

把修复落实为仓库的架构、类型、lint 或测试，防止下一个代理犯同样的错。

## 只问怎么做

```text
/poteto-help 怎么让 poteto-mode 在会话的每一轮持续生效？
```

你会收到答案、可发送的提示词和来源链接。由你发送提示词后才开始实际工作。

## 离开后让运行保持可审计

```text
im going to bed. 自主继续，直到每个 fixture 都通过。用 schedule 按需唤醒，中途别停。保留决策日志供我早上审计。
```

完整约定见[离开后继续运行](./07-overnight.md)。当聊天已包含任务和完成条件时，用短版即可。

## 让跑偏的任务回到正轨

一句话就可以纠偏。

```text
我的目标是复现。先别修。
```

```text
应用 prove it works。给我真实运行输出，构建日志不够。
```

```text
/unslop 清理刚才那段，不用破折号。
```

通常只要点对名称。[原则一页](./08-principles.md)列出了可以直接用的说法。

## 用平实的话重听回复

```text
/bro
```

这就是完整的提示词。[`/bro`](../../skills/bro/SKILL.md) 像人在交谈一样复述上一条消息，缩短篇幅，去掉术语。回复技术上详尽但仍难理解时，用它。

## 回顾离开后仍在运行的会话

```text
/ketchup
```

[`/ketchup`](../../skills/ketchup/SKILL.md) 用平实的话说明你上一条消息之后发生的事，并列出每个等你作决定的事项，附建议、证据和风险。报告过程只读。

想观看简报时，用 [`/ketchup-video`](../../skills/ketchup-video/SKILL.md)。它以带字幕的短幻灯视频说明经过，并在视频下用文字列出等你决定的事项。

## 常见陷阱

- **在提示词里枚举技能。** 「先 `/architect`，再 `/arena`，再 `/interrogate`」会改动 playbook 已定好的步骤顺序。写清目标和约束，只有需要覆盖某项默认时才点名技能。
- **完成条件含糊。** 「改好一点」无法供 `schedule` 唤醒后的流程检查。给出能够判定通过或失败的命令或产物。
- **一开始就给出对原因的猜测。** 代理会沿你指出的方向搜索。先要求它复述问题，再分享你的判断。
- **采用第一个设计。** 只尝试一次，会固化模型最先想到的结构。要求做原型或用 `/architect`，依据证据选择。
- **反复润色抽象计划。** 对没有代码的计划做对抗审查，可能列出不会发生的风险。先用原型回答开放问题，再审阅做出来的东西。
- **多个代理挤在一个 worktree。** 它们会互相覆盖，没人能判断谁改了什么。给每项尝试独立 worktree，或在得到授权的环境里用独立机器的云代理。
- **还未验证循环就让它自动跑。** 无法自行验收的循环会更快地产生未经检查的工作。先跑通验证技能。
- **信任未经核实的数字。** 热缓存或被跳过的代码路径都可能制造加速假象。发布数字前先用 `/benchmark-checklist`。
- **每次都手工纠正同一个错误。** 聊天里纠正只对当轮有帮助。`/correct` 修的是仓库，可以防止后续运行重复犯错。
- **用 `/arena` 做覆盖。** `/arena` 重复同一份设计或代码简报，选一个基础方案并吸收最佳部分。`/pstack-swarm` 分配独立分片或约定好的竞跑分支，然后汇总报告。
- **接受每一条评审评论。** 机器人和人都可能提出真实问题，也可能制造噪声。`/interrogate` 只保留能重跑证实的发现，并说明撤下哪些、为什么。你可以推翻任一判断。
- **把 `auto` 当成模型 ID。** `auto` 和 `inherit-parent` 都表示继承父会话的模型，在 AGY 规则里对应 `agy:inherit`，调用时传 `Model: inherit`。各角色见[安装和配置](./01-setup.md)。
- **构建变绿就报告成功。** 构建能证明代码可编译。要求给出真实命令、流程、存储值或性能分析结果，证据要出现在回复里。
- **直接写 `SKILL.md` 就交付。** 走 [Authoring or modifying a skill playbook](../../skills/poteto-mode/playbooks/authoring-a-skill.md)，完成验证和审阅。

如果是跳读，回到[安装和配置](./01-setup.md)跑一次实际任务。这些做法要用过才记得住。
