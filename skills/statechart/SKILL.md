# 状态图

用读者熟悉的词汇展示系统如何在状态间转换。由读图的人判断行为是否正确。

## 运行

在仓库外的临时目录工作。编写 TLA+ 规约及其配置，再通过 `run_command` 运行下面的命令。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，需要能执行 TypeScript 的运行时。`scripts/statechart` 是负责选择运行时的 POSIX shell 脚本。原生 Windows 上使用 Node 22.18 至 22.x，或 Node 23.6 及以上，运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

首次运行通过 mise 安装 TLC 和 Java，需要联网。

## 编写规约

- 把读者认可的每条规则写成 INVARIANT。规则可描述界面、结果、存储值或消息。如果模型没有表示该规则的变量，添加变量。保持原规则的强度。
- 将 `Next` 写成各动作的析取，例如 `YouPressPlay \/ YouPressStop`。否则 TLC 会把每一步都命名为 `Next`。
- 没有任何出边的状态会违反 `NoDeadlock`，即使它是正确的终止状态。如果已有 INVARIANT 或 PROPERTY 叫这个名字，规则名使用 `CHECK_DEADLOCK`。给 `Next` 添加一个动作，只在终止状态为真且不改变值，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 中为它设置标签。

## 设计图表

状态和箭头的措辞、阶段和配色、标题以及面向读者的报告，都需要你判断。将这些设计写进视图模块，通过 `--view` 传入。

视图导出 `state(vars)`，用读者熟悉的词汇标注状态。返回值决定图表形式。

- 字符串生成平面图。`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组表示父状态层级。`export const state = (v) => v.main.split(".");`
- 对象的每个键生成一个正交区域。`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

按读者可以看到或关心的事给各状态命名，例如 “Paying” 或 “Lease held, write pending”。标签中省去变量名。在 `vars` 里，TLA+ 序列用键从 1 开始的对象表示，所以 `v.pc[1]` 对应 `pc[1]`。集合用数组表示。

视图也可以导出 `step(action, from, to)`。它接收 TLC 动作名及该步骤前后的值，返回箭头标签。按用户眼中发生的事写标签，例如 “you press play” 或 “the connect fails”。省去代码名和 TLA+ 动作名。在图上产生相同终点的两个动作使用相同标签，以便共用一条箭头。

某步只能在某些条件下发生时，用读者熟悉的措辞在标签末尾加方括号条件，例如 `you press play [while the file loads]`。对正交区域图，命令会根据其他区域的标签自动在箭头上写条件，例如 `[when Offline]`。自定义方括号会覆盖这个条件，导致同个起点的两条箭头看起来一样。因此正交区域图里，其他区域的条件由命令填写。若某个未体现在任何标签中的值决定步骤去向，就在标签写结果，例如 “the roster read fails”。

视图还可以导出以下项。

- `group(vars)` 返回阶段名。图上每个状态采用所属分组的颜色。若同一图表状态背后的模型状态属于不同分组，该状态不着色。
- `colors` 为每个分组名指定一个颜色类。
- `title` 是显示在图表顶部的字符串。

命令对每个模型状态最多分别调用一次 `state()` 和 `group()`，对每个步骤最多调用一次 `step()`。图表和报告共用这些返回值。让每个函数只依赖其参数。

图表不绘制起点和终点标签相同的步骤。读者必须看到这类步骤时，拆分标签。

箭头尽量控制在 20 条左右或更少。太多就不易读。先让 `state()` 返回更粗粒度的标签。行为相同的值用同一个标签，省去读者无须知道的细节，例如返回后什么也不改变的进行中调用。保留缺陷路径上的每个状态和各处标记。把 `breaks` 合并成 `mayBreak` 会隐藏规则违反的位置。违反不同规则的两个状态应分别保留，以免读者无法对应位置和规则。如果图仍太忙，可以让 `step()` 为读者无需了解的步骤返回 `null`。例如每个状态都有的重置步骤，或重复其他箭头信息的步骤。隐藏步骤须遵守以下规则。

- 各图表状态仍可沿箭头从某个起始状态到达。
- 模型有出边的每个图表状态至少保留一条出边。
- 一条箭头对应的步骤全隐藏或全保留。只隐藏部分步骤会收窄该箭头的条件。
- 交付时说明图里隐藏了哪些步骤。

## 阅读报告

- 违反规则的状态使用 `breaks` 类。只有该标签下部分模型状态违反规则时用 `mayBreak`。图例（Legend）列出各标记对应的规则。两条规则同时违反时，图例会把两条写在同一标记上，交付时应说明各状态违反哪条规则。对正交区域图，包含某状态的每种区域状态组合都可能违反规则时，该状态会带标记。若某个组合可能违反规则而其中的状态都没有标记，则标记该组合中的所有状态。
- TLC 会越过违反规则的状态继续探索，所以图表能显示出错后的状态。
- 因为 TLC 会继续探索错误之后的路径，状态数无界的模型可能一直运行。把常量控制在小范围内，或添加 CONSTRAINT。
- 有 VIEW 或 SYMMETRY 时，TLC 将它视为等价的状态合计为一个，图表也只绘制这一个。箭头可能指向这个代表状态，实际动作可到达另一个等价状态。报告会说明。
- TLC 检查超出 CONSTRAINT 或 ACTION_CONSTRAINT 的每个状态是否满足规则，但不探索该状态，也不检查它是否死锁。某条规则的最短违反路径若在这种状态结束，图表会画出该状态，报告会给出路径。其他超界状态不画，超界状态中的死锁也不可见。对每个被 ACTION_CONSTRAINT 排除的步骤，TLC 同样检查步骤之后的状态是否满足规则，即使它通过别的途径也能抵达下一状态。某条规则的最短违反路径若以此类步骤结束，图表会画出这一步。
- 命令用一个 worker 按原配置运行 TLC 检查规则。一条规则被违反时，命令移除该规则后再次运行，直到不再有规则违反。发现第一条违反规则后，后续每次运行在 100,000 个不同状态处停止，以免大模型无限运行。达到上限或因错误停止时，报告在 “Rules not checked” 下列出未检查的规则，图中也不标记它们。未检查的规则既可能成立，也可能被违反。要检查这些规则，可以从配置中移除已经违反的规则，或缩小模型。上限会引入一个模块，改变 TLC 的变量顺序，因此对 PROPERTY，TLC 可能找到和无上限时不同的反例。
- `tlc.out` 保存 TLC 按原配置打印的输出。如果图表未显示某条违反规则的缺陷路径，`tlc-RULE.out` 保存找到它的那次运行的输出。TLC 重复自己的第一条警告时，原生 TLC 打印两次，而 `tlc.out` 只显示一次，因为命令读取的输出不含第二份副本。仅当 Java 使用 `-XX:+UseParallelGC` 时会有这种重复。否则第一条警告就是建议加上该参数，只打印一次。

## 展示图表

将 `chart.mmd` 作为 `mermaid` 代码块展示给用户。图表上限是 500 个状态，以 TLC 按原配置统计的数量为准。超过上限时，图表只绘制通往违反规则的状态的路径。如果没有规则被违反，命令不会写 `chart.mmd`。命令仍检查每条规则，报告仍给出状态数和各条缺陷路径。要查看完整状态图，缩小模型。

用 Pele 渲染图表。用户要求图片，或图表太大、文本难以阅读时，按 `references/render.md` 操作。只有用户提出要求时才用其他渲染器。

## 交付

把每张图及其 Mermaid 文本交给需要作决定的人。每个缺陷用一行列出规则、按读者措辞写成的规则描述，以及报告中按编号给出的路径。说明模型排除了哪些内容。给出重新生成这些文件的命令，使用新的 `--out` 目录。

模型描述代码时，对真实代码逐动作重放每条缺陷路径，可用测试或实际复现。如果缺陷没有出现，先假定模型有误，直到证据证明模型正确。
