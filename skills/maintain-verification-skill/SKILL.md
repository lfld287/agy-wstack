# 维护验证技能

应用一改，功能地图就可能过时。本技能用于维护由 `/create-verification-skill` 生成的技能，或任何带功能地图的项目级验证技能。以功能为验证单位。每个功能文件都要对照源码，每项功能都要实际操作一遍，无需把文档逐条搬到终端执行。

## 结果

选择一种并说明。

- **准确（clean）。** 每项功能都有源码和实测覆盖，没有值得交付的修正。无需创建分支或 PR。
- **有改动（changed）。** 最多用一个 PR 交付经验证的文档、工具链或地图修正。
- **受阻（blocked）。** 覆盖无法完成，或已验证的修复无法安全交付。说明具体阻碍。

## 编辑范围

只编辑验证技能自身的目录，包括 `SKILL.md`、`features/` 和归它所有的辅助脚本。本轮不编辑产品代码。地图描述了应用已经没有的行为时，判断是文档漂移还是产品回退。前者修地图，后者如实报告并保留文档中的既有承诺。

## 维护流程

0. **定位目标。** 查找正文包含启动、驱动和功能地图的项目级技能。通常位于 `.agents/skills/verify-*/`，或项目已有的技能目录。有多个候选时用 `ask_question` 确认。没有候选就停止，并指向 `/create-verification-skill`。

1. **整理索引。** 用 `read_file` 阅读功能地图 README，用 `run_command` 配合 `rg --files` 或 `find` 列出同目录文件。修正遗漏、多余、重复或失效的条目。保持核对简单，无需生成清单。

2. **并行审读源码。** 每个功能文件用 `invoke_subagent` 并行启动一名只读子代理，例如 `Model: "flash"`、`Workspace: "share"`。特别注明禁止驱动应用、禁止编辑文件。各自从源码回答「用户看到的这个功能如何工作」，指出可能与文档不符的地方并给出处，再提供一条简短的实测步骤。返回格式为功能摘要、源码入口、疑似漂移或无漂移、实测步骤。

3. **汇总。** 确认每个功能文件都收到了摘要。合并重叠步骤，尽量减少所需的应用状态。抽查有引用的疑似漂移，无须重新证明已通过源码核对的说法。查看近期改动是否引入地图未收录的用户入口。有具体源码路径才能确认遗漏。

4. **实际操作。** 即使看源码没发现问题，也必须实测。主代理独自负责操作，按目标技能「启动」一节指定的模式运行。服务和 UI 通过一个长驻实例串行驱动，短生命周期 CLI 则为每次操作用一个新的独立会话。每项功能至少操作一次。无论哪里失败，全程保持三项要求。
   1. 首次操作前先做 doctor。按会话隔离时，每次开新会话都做 doctor。一次操作失败后，先再做 doctor，然后才能继续。若 doctor 看不出故障，例如进程健康但 UI 卡住，须重置到已知状态或重启。
   2. 已采集的证据必须在每次清理后留存，到约定位置实际确认。
   3. 本次操作启动的东西，完成其用途后立即清理。无论会话卡住、退出还是共享，都清掉失败尝试留下的状态。共享实例只清残留，保留实例。

   技能漂移造成的 doctor 失败也属于漂移。先在允许的编辑范围内修复，重试一次，仅重启受该修正影响的部分，再判断是否 `blocked`。功能只能在记下具体前置条件和尝试入口的情况下标为 `verified-unreachable`，例如缺少认证、授权、特定操作系统或外部状态。地图漏写前置条件也算漂移。排查中修过的工具链必须实际重跑证实。整轮最后一次操作及这些复验完成后做最终清理，确认本轮启动的东西都已收尾，证据仍依技能约定保留。

5. **归类处理。** 用户视角的描述错误或遗漏，属于文档漂移，修正文档。功能本身正常但工具链无法驱动，属于工具链缺口，修工具链，沿用生成时的辅助工具规则：脚本可执行，技能正文中给出调用方式。实际应用出错时，记录为产品问题并报告用户，放在本次 PR 范围之外。

6. **交付或结束。** `changed` 时先重读每个改动文件，有授权时只开一个 PR，提交已经证实的修正，仅获本地编辑授权时就本地交付。`clean` 或 `blocked` 时无需 PR，如实汇报结果和覆盖。

在临时位置保存简短运行记录，包括已覆盖的功能、不可达的前置条件、已证实的漂移和结果。这些记录不入提交。
