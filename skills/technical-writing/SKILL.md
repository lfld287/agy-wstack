# 技术写作

让疲惫的工程师读一遍就懂。

- 删掉不提供信息的词。
- 选简短的日常用语，例如用 “use” 代替 “utilize”。
- 遵守规则会让句子更差时，换个写法，或保留原句。
- 直接写真实的符号、文件、参数或命令名，避免换同义词或绕着描述。
- 别造术语。用开发者说得出口的词。首次提到某个有名字的模式时，解释它的含义。

## 调整节奏

- 长短句交替。一句承载两层意思时拆开。只讲一件事的长句可以保留。
- 解释可以有观点，参考资料只写事实。
- 用具体结果，例如把 “schema changes can cause issues” 改成 “a column rename fails the build”（重命名列会导致构建失败）。

## 先确定文档类型（Diátaxis）

每份文档只用一种类型。需要多种时拆开，用链接串起来。

- **教程。** 让读者动手学习。说明学完会做出什么。每一步都有可见结果，写清读者会看到什么。解释只占一个分句，加一个链接。
- **操作指南。** 按步骤达到目标。解决读者手头的问题，按读者具备相应能力来写。只写行动，允许分支。用要完成的任务命名。
- **参考资料。** 供人查事实。只描述，平实、完整、确定。结构遵循被描述对象本身的结构。
- **解释。** 帮助理解事物及其成因。主题要有边界。给出设计决定、历史、约束和备选方案等背景。只有解释可以写观点。

## 面向读者写句子（Google 开发者文体）

- 用第二人称「你」，用现在时。
- 写清谁做什么。只有行动者未知或无关紧要时才用被动语态。
- 用祈使句写操作指令。条件放在指令前，常见情况放在前面。
- 避免时髦术语、比喻和「请」。在流程里禁用 “simply”、“easy” 和 “quickly”。
- 直接说内容，避免提前预告。连续的句子避免用同一个短语开头。
- 让链接文字说明目的地。
- 标题直接表达要点。英语标题用句首大写。每页只有一个一级标题，标题层级不跳级。
- 有先后顺序的内容用编号，其他内容用项目符号。用完整句子引出列表。列表项句式保持一致。
- 代码用等宽格式，界面元素加粗。英文列表使用牛津逗号。省略 “etc.”。

## 每句话只承载一项内容（STE 规则）

- 一句话给一条指令。其他句子一律只讲一件事。
- 英文指令超过约 20 个词、其他英文句子超过约 25 个词时拆句。
- 警示或条件放在它限制的步骤之前。
- 英文保留 “the” 和 “a”。
- 一个词只表达一个意思。一个动作只用一个说法。
- 用直接命令写流程，避免叙述和被动语态。
- 英文尽量少用以 “-ing” 结尾的形式。

## 消除歧义（Global English）

- 将 “only” 和 “not” 等词紧贴被修饰的词。
- 拆解一长串名词。
- 让 “it”、“they” 和 “this” 各自明确指向一个对象。禁止用 “this” 或 “which” 指代整个分句。
- 保留动词及 “that” 等用来标示结构的小词。
- 若重复冠词能避免误读，就在并列项中重复冠词。交代清楚 “and” 或 “or” 连接哪些内容。
- 用句号断句，避免分号和破折号。避免斜杠和 “(s)”。括号内的文字要构成完整的语法单位。
- 同一个对象始终用同一个名字。
- 省去惯用语、口语套话、拉丁语缩写和隐喻。

## 文风和仓库约定

- 本技能处理的每篇文档都应用 **unslop**。由它维护 AI 用词、填充语、含糊限定和格式习惯的清单。
- PR 描述和提交信息也适用。除 Diátaxis 外，各层规则都适用。PR 正文是一份评审者不到一分钟能读完的简报。子代理日志、SHA 清单和指标表用链接提供。
- 产品界面文案遵循产品自身的文案指南。
- 代码片段用制表符缩进。写真实路径。对数量和目录树的描述须在落地提交中成立，并附上能重新生成结果的命令。
