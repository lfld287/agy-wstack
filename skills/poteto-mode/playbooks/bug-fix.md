### 缺陷修复

**由你主导任务，负责规划、审查和验证。** 将调查和修复委派给子代理。按[自主执行](autonomous-run.md)的 AGY 调度约定，为各子代理选合适的模型和推理强度。

交付的每一行都应有运行证据。任何「也许有用」的额外防护只是假设，不能当修复交付。证据否定一个假设时，撤回它引出的全部改动。提交证据支持的最小改动。

1. 用相应的控制手段在同一使用界面亲自复现（见[执行约定](../SKILL.md#执行约定)）。即使调试或插桩流程让你请用户复现，也先自己跑到控制手段所能达到的最远处。只有明确说明为何无法触达目标后，才用 `ask_question` 请用户协助。若直接复现不了，构造触发条件、收窄条件或插桩，直到问题出现。
2. 用二分思路定位原因。先跟踪受影响的子系统，用 **why** 查回归历史，列出假设再逐个排除，直到只剩一个。每轮先做最能缩小范围的切分，取得运行证据，再淘汰假设。程序状态不清楚就插桩或加日志，并在代码运行时读取。排查耗时或进展困难时，用 AGY `schedule` 或 `/schedule` 驱动排查。先用运行证据确认仍成立的故障机制，再进入第 3 步的 `architect` 或并行开展 `interrogate`。
3. 规划修复。跨函数边界时先用 `architect`。按模型配置中的 `bug-fix` 角色委派实现，原生 AGY 默认用 `Model: "pro"`，也可按角色用配置的外部模型。交代具体修改范围。
4. 在同一使用界面验证原复现用例已经通过。结果不确定或验证界面不符，一律标明未通过。单测只证明命中的分支行为，要另行证实原缺陷已消失。
5. 组织提交，让 Git 历史先记录失败的复现用例，再记录修复。有低成本的本地测试路径时，按 **tdd** 先写会失败的测试。成本高、集成依赖重或路径不清晰时跳过。
   这是 **principle-sequence-verifiable-units** 的典型用法，先提交失败的测试，再叠加修复。
6. 执行[开 PR](opening-a-pr.md)。

**回复**应说明缺陷、根因、修复和验证方法，逐字粘贴修复前失败、修复后通过的复现输出。
