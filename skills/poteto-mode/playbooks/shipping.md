### 交付

**由你负责决定哪些 PR 能合入。逐个独立验证，从栈底合入连续通过的部分，期间不要改动堆栈。**

1. **先选托管平台的 CLI，每个 PR 都独立验证后再合入。** 默认用 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能识别仓库，全部 PR 操作统一用 `origin pr`。否则继续用 `gh` 并记下回退。无需 Graphite（`gt`）。每个 PR 安排一名未参与编写代码的验证者。按[自主执行](autonomous-run.md)的调度约定，用 `invoke_subagent`（例如 `Workspace: "branch"`）或独立工作树里的 `codex`、`pi` 后台任务。验证者用匹配的手段按用户用法操作，比较父版本与 head，再在 PR 上发布 `PASS`、`PASS+NOTES` 或 `FAIL`。在 AGY 中，UI 可用浏览器自动化或 CDP，CLI 可用 PTY 或终端驱动。实现者容易只验证自己本来要做的事，CI 通过和评审机器人批准也不能代替用户场景验证。
2. **只合入从栈底开始的连续已验证区段。** 从最底部未合并的 PR 向上检查，遇到首个缺少 `PASS` 或 `PASS+NOTES` 的 PR 就停。它下面的 PR 组成待合并区段，最上方一项是本轮上限。已验证但位于未验证 PR 之上的 PR 要等底下的代码先合入。如果某分支既不包含也不依赖下层代码，可以迁到主干独立合入。迁移后须重新验证，原结论是在含下层代码的基线上得出的。
3. **核对验证结论仍对应这份代码。** 结论对应补丁。堆栈 rebase 会把所有上层 PR 推到新 SHA，现有检查可能仍全绿。沿用旧结论前，比较作出结论时的 SHA 与当前 head 的补丁 `git patch-id`。当两份补丁只在测试、文档或 lint 配置上有差异，且该项验证用到的产物在两个 SHA 上的构建结果除噪声外一致时，可沿用该项结论。噪声指同一验证 SHA 构建两次也出现的差异，或产物中嵌入的提交 SHA。逐类报告噪声及涉及的文件，以便复核。改动本身仍须重新检查和评审，旧结论未覆盖它。开发服务器等没有构建产物的验证项无法用此方法证明一致，须重跑。其他已发生漂移的验证也要重做。
4. **自底向上，每次只合一个 PR。** 始终合并区段中最底部未合并的 PR。用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。在 Origin 中，普通合并命令也会合入所指定 PR 下方的全部 PR。在 GitHub 中，基线仍是父 PR 分支时会合到该分支。随后用 `origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName` 回读结果。合并命令显示成功可能只是进了队列，启用自动合并也不能算已合。只有读到已合并且基线为主干，才算落地。只有验证结论覆盖当前 head 时才可用 `--auto`（Origin 的就绪即合并或 GitHub 的自动合并），因为它会合入达到就绪条件时的 head。一个 PR 真正合入后，把原以该分支为基线的上层 PR 改到主干（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），将它的补丁移到合并结果上，用 `--force-with-lease` 推送。结论对应补丁，用第 3 步的 `git patch-id` 规则判断是否仍有效。检查通过且结论仍有效即可合并。
5. **合并期间保持堆栈稳定。** 只按第 4 步调整下一个 PR 的分支或基线。合入的是当时分支和基线上的内容，即使该内容与结论不一致。GitHub 上用 AGY `schedule`（或 `/schedule`）定时运行 `scripts/watch-pr/watch-pr --queued-stack`，直到脚本在区段上限报告 `COMPLETE`。用 `--stack-prs` 按自底向上的顺序传入本轮 PR 编号，每次重启监视器时传同一列表。Origin 上每次 `origin pr checks <pr> --watch` 返回后，都用 `origin pr view <pr> --checks` 重读当前 PR，直到上限 PR 显示已合并。父 PR 合并后，子 PR 基线移到主干是预期行为。合并卡住时先查原因，再改任何东西。
6. **到本轮上限为止。** 要扩大区段，须从第 1 步重新取得验证结论。

**回复**应包含连续已验证区段和上限、每个 PR 的结论及验证者、已合入内容和确认方法，以及下一处缺口需要什么。
