### 性能问题

**由你负责规划、审查和核实测量结果。** 每项修复都要对应实测数据，读源码不能代替测量。

1. 用匹配的控制手段采集基线追踪。按 **benchmark-checklist** 核对基线和之后的每个数字。
2. 跟踪代码，给假设找依据。先实际运行，再谈性能上限。
   按成本从低到高尝试以下做法。
   1. 取消结果无人使用的工作。
   2. 做一次，避免重复。
   3. 少做一些。
   4. 晚一点做。
   5. 在用户感知不到时做。
   6. 并行做。
   7. 降低单次执行成本。

   靠前的做法已达标，就不用继续往下试。
3. 按追踪结果规划修复。跨函数边界时先用 `architect`。按模型配置的 `perf-issue` 角色委派实现，原生 AGY 默认 `Model: "pro"`，也可用配置的外部模型。按[自主执行](autonomous-run.md)的 AGY 调度约定，为每项任务选合适的推理强度。审查差异，然后采集修复后的追踪。
   按 **principle-sequence-verifiable-units** 逐次验证，每次通过检查后再试下一项。
4. 解析并比较产物，例如把 JSON 导入 SQLite 后对比。结果不确定或验证界面不符，一律标明未通过。
5. 在 PR 中引用测量结果。
6. 执行[开 PR](opening-a-pr.md)。

需要对同一个指标持续优化时，使用[迭代优化指标](hillclimb.md)。

**回复**应包含基线数值、修复后数值、差值和产物路径。
