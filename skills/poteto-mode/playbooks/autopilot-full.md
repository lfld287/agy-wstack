### 全程自动推进（autopilot-full）

**你负责作出验证结论。每个 PR 由一名负责人从实现跟到合并。合并前，由未参与编写代码的 `swarm` 验证组证明实际会合入的代码可用。**

验证结论对应一份补丁，CI 通过对应一个 head。第 4 步完整运行一次 `swarm`，仅在重大改动后重跑。[交付](shipping.md)的 `git patch-id` 规则允许沿用单项验证的结论。每个新 head 都要重新通过 CI。

1. **先遵守操作者设定的关卡。** 授权仅覆盖队列内的事项。操作者明确留给自己的事项以及队列外的 PR，都停在可合并状态。要求陈述计划不等于同意执行。
2. **每个 PR 派一名负责人，把工作留在接手者能找到的地方。** 派工前确定唯一的根决策日志的绝对路径，例如 `<workdir>/decisions.tsv` 或 `<workdir>/.audit/<task-slug>.tsv`，其中 `<workdir>` 是根代理工作目录的绝对路径。每份派工简报都写明当前已加载手册的绝对路径，并要求负责人在回报中提供结构化决策条目。根决策日志只由根代理串行追加。整批任务只选一次托管平台的 CLI。默认用 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能识别仓库，全部 PR 操作统一用 `origin pr`。否则继续用 `gh`，并记下回退。无需 Graphite（`gt`）。用 `invoke_subagent` 和 `Workspace: "branch"` 启动负责人，也可按[自主执行](autonomous-run.md)的调度约定，派 `codex` 或 `pi` 后台任务使用独立的本地 `git worktree`。负责人实现改动，按[开 PR](opening-a-pr.md)创建 PR，在真实产物上举证，按[盯 PR](babysit.md)跟进到 CI 通过，待第 4、5 步放行后合并。盯 PR 手册要求报告 rebase 时，由负责人 rebase 自己的分支，再用 `git push --force-with-lease` 推送。

   尽早开 PR，让 CI 和评审机器人与实现并行。对照差异人工清理冗余和生成式套话，完成 `no-comments` 检查，才算代码就绪。这两项在 AGY 中对应 Cursor `cursor-team-kit` 的 `/deslop` 和 `/no-comments` 流程。完整 `swarm` 审的是这份成品。随后 rebase 到当前主干，在自验之前报告代码就绪时的 head，让验证基于补丁将合入的基线开展。此后每个新 head 都要报告。自验、CI 和盯 PR 都完成后，报告已可合并。修复轮次沿用该基线，除非主干产生冲突、导致 CI 失败，或已有并行改动落到同一批文件上，因为每次 rebase 都会重启 CI。在推送代码就绪的 head 前，以及之后任何需要重新验证的推送前，对已提交的 head 运行仓库为受影响路径规定的检查。

   按工作环境随时可能丢失来准备。启动后尽早推送，并按 **show-me-your-work** 在阶段回报中提交结构化条目，逐条给出时间、阶段、决定、理由、证据和结果。完成一个工作单元就先推送，再做下一个。派出子代理或后台任务的人也要回报任务 ID、状态，以及根据以往同类任务估出的卡住阈值，便于父代理失效时由根代理探查。根代理收到回报后逐条追加到根决策日志。只强推自己的分支，并让 `--force-with-lease` 明确绑定到上次推送或接手时的 SHA。发现任何别人对该分支的推送，立即停止并报告根代理。
3. **各负责人从主干并行分支，PR 不堆叠。** 每个 PR 独立合入。
4. **完整运行一次 `swarm` 验证。** 首次在代码就绪的 head 上运行。只有新增行为、重新设计或新增大段差异才重跑完整验证。rebase、解决合并冲突或小修后，在新 head 上安排一名验证者。仅改措辞可免复核。按 `swarm` 在代码就绪的 SHA 上并行派独立验证者，可混用 `agy:*` 和外部 CLI 的不同模型。验证者重跑关卡，使用匹配的控制手段（AGY 中可用浏览器自动化或 CDP 验证 UI，用 PTY 或终端驱动验证 CLI，也可指定其他驱动）在真实使用界面验证关键行为，并审查差异。必须有实际运行验证，并由你核对可合并报告里的凭据，才能给出无保留的通过结论。每个验证方向都要自己核实主张。

   阻塞 PR 要举证，例如当前 head 上的失败记录，或本 PR 改错的文档行。基线已有的问题，无论基线是主干还是栈中下层 PR，都不构成阻塞，除非本 PR 复制了问题或让新的路径触及它。只有用户会遇到的缺陷、失败的关卡或会随之交付的错误文档才阻塞，其余记为后续工作。
5. **负责人只合并已验证、且在实际合入基线上测过的代码。** CI 通过本身不授予合并权限。各项 `swarm` 验证启动后，进入合并准备，把分支 rebase 到当时的主干，报告新 head，等 CI 通过。

   合并前立即 fetch 主干，判断它的变化是否会影响补丁，避免主干每动一次就 rebase。若实际合入的代码尚未测过，例如有冲突、两边改了同一文件，或 PR 应跑的检查发生了变化，就 rebase 并等 CI。两边都改了锁文件时，如果在合并结果上锁定依赖安装通过，且本 PR 涉及的包在合并结果上的解析与 head 一致，可跳过 rebase。该安装已检查会合入的锁文件，若失败则必须通过 rebase 修好。若主干改了补丁的调用方或补丁依赖的内容，例如被调用的代码或依赖版本，在合并结果上跑补丁对应检查，通过后合并。其余情况直接合并。若主干变化会迫使合并准备阶段再做第三次 rebase，暂停并报告根代理，由根代理给冲突工作排顺序。
6. **履行根代理的职责。** 放宽关卡的任何改动，例如提高预算上限或增加允许列表条目，先由验证者提供证据，再由你重新签核。负责人本身有让检查变绿的动机。若授权含批准权，该签核即为批准，负责人应记录签核出处，供验证者核对。撤掉禁用检查或把失败改为非阻塞的改动，因为它们会使检查失去对所有情况的约束。托管平台强制的审批不得代批或绕过，根代理签核也不能替代。

   操作者同意后，用 AGY `schedule`（或 `/schedule`）每小时唤醒根代理审计，例如 `CronExpression: "0 * * * *"`，直到没有委派事项再取消。定时唤醒提示须写入根决策日志和当前已加载手册的绝对路径。每次唤醒按提示中的路径读取根决策日志并重读手册，让负责人补报遗漏的 head 或任务 ID，由根代理追加记录。逐一探查所有代理和后台任务，直至最末端的验证者，按实际动作判断进度，例如提交、验证产物和记录变更，状态文字和摘要可能掩盖卡住的任务。任务报错、无法开始新一轮、超过阈值仍无新产出，或负责人到首次审计时既未推送也未回报决策条目，均视为卡住。等待你或操作者答复的任务要先得到答复。卡住就立即换人接手，别等原任务停止后才派替补。影响操作者的状态有变化时，按 **ketchup** 补报。无变化则保持安静。
7. **操作者叫停时立即停。** 向所有负责人下达零写入指令。每人报告当前状态，保留任务简报，等待操作者解除暂停。

**回复**按 **ketchup** 同步各 PR 的状态和验证结论、已合并项、签核及理由、待操作者放行的关卡和搁置的后续事项，附各 PR 和记录轨迹的链接。
