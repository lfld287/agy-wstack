### 迭代优化指标

**由你负责指标和实验完整性。监督和审查，把每次尝试交给子代理。** 本手册适用于针对一个可量化指标持续迭代。单次修复参见[缺陷修复](bug-fix.md)或[性能问题](perf-issue.md)。

每次做一项改动，测一轮，再决定保留或撤回。禁止叠加未经验证的改动。按 **principle-prove-it-works** 实测，读代码不能作为优化成效。

1. 先摸清负载和架构，再选指标。跟踪目标，列出实际会影响结果的负载维度，例如数据量、历史、状态和并发，选能复现用户问题的场景。复现不了就先修复复现条件。然后固定一个指标、改进方向和可检查的停止条件，停止条件同时规定目标和最低尝试次数，防止一次偶然的早期收益结束整个过程。例如「比基线至少好 50%，且至少完成 10 轮」。用户给了数字就用，没给就与用户约定。
2. 按 **principle-build-the-lever** 建好测量工具，证明它能辨别差异，然后冻结。运行有对照的真实负载，确认目标负载能复现症状，较轻负载也能如预期区分开。区分不了就调整负载或指标。冻结前用 **benchmark-checklist** 检查，令工具输出错误数和实际完成的工作量。冻结后，只用一条可重复的命令输出指标，多采样压过噪声，例如取 N 次中位数。改动前记录指标基线，并跑通必须保持通过的回归关卡。
3. 按 **show-me-your-work** 建立决策日志 `decision.tsv`，每次尝试一行，记录编号、假设、改动、改动前后数值、差值、测试、结论（保留或撤回）和备注。每次尝试前重读。日志留在版本控制之外，使用 Git 忽略的路径。
4. 用第 1 步的架构模型支撑每个假设，说明具体机制，例如「把 X 移出启动路径，X 目前会阻塞首帧渲染」。避免「试着缓存点东西」这类宽泛猜测。优化性能指标时，按[性能问题](perf-issue.md)第 2 步的顺序排列假设，仅沿用尝试顺序。
5. 循环，每轮只检验一个假设。
   - 按模型配置的 `hillclimb` 角色委派改动，原生 AGY 默认 `Model: "pro"`。按[自主执行](autonomous-run.md)的调度约定选择模型及推理强度。交代紧凑的修改范围。按 **principle-guard-the-context-window** 监督并审查差异，把具体编辑交给子代理。有多个独立假设时，按 **principle-separate-before-serializing-shared-state** 并行验证，每个任务用独立工作树。可用 `invoke_subagent` 的 `Workspace: "branch"`，或让 `codex`、`pi` 后台任务使用各自的本地 `git worktree`。
   - 用已冻结的工具测改动前后数值，再跑回归关卡。
   - 只有指标改善超出噪声且回归关卡通过才保留。否则完整撤回，包括任何「也许有用」的调整。
   - 每个保留的改动单独提交，只暂存自己改的文件（`git add <files>`，禁用 `-A`）。无论保留还是撤回，都记一行。
   按 **principle-sequence-verifiable-units** 做完本轮检查，再开下一轮。无人值守时只沿用[自主执行](autonomous-run.md)的唤醒机制，本手册自己的停止条件仍有效。
6. 越过第一次平台期。接连否决数个尝试时，换一类假设，组合接近达标的尝试，重读源码，或试更彻底的做法，再判断是否确实没有空间。正确性和简洁性优先于数字。按 **principle-laziness-protocol** 撤回破坏行为的收益，保留指标持平且降低复杂度的改动。
7. 达到停止条件，或只剩收益边际、成本不划算的思路时停止。不得降低目标凑达标，也别在还有低成本假设时停手。确实卡住就报告，避免空转。
8. 执行[开 PR](opening-a-pr.md)，按实际接纳顺序叠放保留的提交。

**回复**应包含指标和目标、基线与最终值及变化百分比、总轮次及保留和撤回数量、每项保留改动的一行说明、`decision.tsv` 路径，以及继续优化时最值得尝试的方向。
