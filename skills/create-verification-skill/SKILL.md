# 创建验证技能

需要有一套脚本能驱动真实应用并证明其行为。启动应用，按用户的方式操作功能，采集证据。本技能据仓库情况生成项目级技能 `<skills>/verify-<app>/`。在 AGY 中，`<skills>` 为项目内的 `.agents/skills/`。项目已有约定的技能目录时，沿用该目录。生成的技能写给下一位代理，它可能在任务途中第一次接触此应用。

## 1. 从仓库找答案

先查代码库，只对无法观察的问题用 `ask_question` 询问用户。

- **用户入口。** 用户实际接触的是 Web 界面、CLI/TUI、桌面应用、API、移动应用，还是库？仓库可能有好几种入口。选一个主要入口并记录其余入口。
- **启动。** 应用怎样在本地启动？优先采用仓库已有文档里的开发命令，例如包脚本、Makefile 或 README 快速上手。记下端口、环境变量、种子数据和认证要求。
- **驱动。** 代理如何用程序操作应用？先找现有工具链，例如 Playwright/Cypress 用例、expect 脚本、PTY 辅助工具、可用 curl 调用的端点或调试端口。没有时再选通用方案，例如用浏览器或 CDP 驱动 Web 和 Electron，用 tmux 或 PTY 驱动 CLI/TUI，用普通 HTTP 驱动服务。
- **观测。** 哪些可作为证据？例如截图、终端记录、响应正文、日志、退出码、数据库状态。
- **隔离。** 两个实例能否并行运行？核对端口、数据目录和配置档案。不能隔离就在生成的技能中写明，避免两个验证同时操作共享实例而破坏用户的会话。

当前检出内容如果无法直接构建或启动，在生成前先修复或精确报告问题。基线跑不通会让技能教错步骤。如果只缺少与验证无关、却妨碍启动的资源，例如 API 永远不会提供的静态目录或一份示例配置，可以在生成的技能中创建它，将其明确标为验证用辅助资源，并在清理阶段移除。

## 2. 生成技能

用 `write_file` 写入 `<skills>/verify-<app>/SKILL.md`。使用 YAML frontmatter，设置 `name: verify-<app>`，在 `description` 写出应用名、用户入口和使用时机。技能注册依赖 frontmatter。按仓库中查到的实际情况填写以下章节，确保没有占位符。通过 AGY 的 `run_command` 执行本地命令，Web 应用接入可用的浏览器驱动或仓库自带工具。

- **启动。** 写清为验证启动应用的准确命令，以及就绪信号，例如一行日志或提示符。应用必须从空数据目录进入可用状态，包括必要的迁移和种子数据。仅有进程响应并不足够，例如数据库初始化脚本仍在跑时，健康检查也可能通过。给出拆除方式。短生命周期的 CLI/TUI 无需保活服务器。这里的启动指先构建一次二进制文件或安装依赖，再为每次驱动启动独立的 PTY 或 tmux 会话。
- **自检（Doctor）。** 提供一项只读检查，回答「现在能操作这个实例吗」。确认进程在运行、版本或构建正确、端口确实由本次启动的实例占用且认证有效。出现异常时先做这一步。
- **驱动。** 使用本仓库的真实选择器和命令给出操作方法。优先采用稳定标识，如 ARIA 标签、数据属性、提示符文本和路由路径，减少对坐标或 Tab 顺序的依赖。
- **证据。** 说明采集内容和存放位置，并规定证明标准。走真实用户路径，避开内部 setter 或仅测试可用的端点。记录用户操作和结果状态。除可见变化，还要核对文件写入、插入的数据行、发出的消息等副作用。只有生产代码已在边界隔离外部系统时，才在该边界使用模拟。需要用 dry-run 或测试模式控制副作用时，观察文件、网络和 Git 引用，实测该模式跳过了什么。有些 dry-run 仍会访问网络或打开浏览器。
- **清理。** 清理本轮启动的实例和临时状态。只终止确由本轮启动的进程，禁止按进程名批量终止。证明产物要在拆除后留存，技能里写清其存放位置。
- **辅助工具。** 技能随附的脚本必须可执行，在正文里给出调用命令，接手者应能直接使用。

## 3. 建立功能地图

创建 `<skills>/verify-<app>/features/README.md`。从路由、命令、菜单或文档识别面向用户的功能，先选主要的 3–5 个，每个功能一个文件。沿用 [功能地图示例](references/feature-map-example/) 的结构，用 README 做索引，每个功能单独成文。每个文件从用户视角回答功能是什么、怎么进入、怎么用工具链操作，以及什么样的可观测终态能证明它有效。依次使用四个二级标题 `子功能`、`如何进入（用户视角）`、`使用 <harness> 驱动`、`注意事项`。`<harness>` 替换为实际工具名称。种子数据不满足某条操作路径的前置条件时，该路径记为失败并在该功能的「注意事项」写明原因。禁止放宽操作路径求通过。功能地图是仓库持续维护的验证依据。地图列出多个入口时，只走其中方便的入口，证明就不完整。

## 4. 交付前跑通生成的技能

按技能自己的说明完整跑一轮。启动、自检、驱动一个已收录的功能、采集证据，再清理。验证一个功能即可证明这套流程跑得通，功能地图供以后的运行覆盖其余功能。清理后，确认指定位置的证据仍在，误删证据则本步骤失败。修掉失败点，每次尝试失败后也执行生成的清理流程，以免遗留进程和端口。未实际执行过的生成技能仍是草稿。如果用了替代环境，例如用容器代替新建虚拟机，或用本地服务栈代替远程服务栈，逐项列出替代环境执行了而真实目标不会执行的配置步骤。只有在实际目标上跑过，才能确认这些步骤。

## 5. 告知如何后续维护

提醒用户随着应用演进，用 `/maintain-verification-skill` 保持功能地图准确。只有用户询问时才建议运行频率。
