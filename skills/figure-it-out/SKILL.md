# 制定方案并执行

任务不适用任何既有流程时，设计一个。写代码前先交付工作流程。把工作拆成多个阶段，按任务风险定验证要求，用可检验的假设推进，并留下用户暂离后仍能审计的决策记录。

## 开始

创建待办列表，第一项是阅读 **poteto-mode** 的「原则索引」部分，并将以下各阶段加入列表。

## 阶段 A 界定任务

先查清现状，再承诺执行。至少能说明以下三项才开跑。

- **完成条件。** 写成一个可证伪的判定条件，参见 **principle-prove-it-works** 原则技能。
- **量化范围。** 给出大致的工作单元、工作量，以及调查中发现的阻碍。
- **严谨程度。** 默认标准偏高。不可逆的决定和影响面大的改动需要更严格的验证，低风险且可逆的步骤可以从简。用验收关卡和产物体现严谨程度。

投入长时间执行前，先给出任务界定和取舍。可逆工作继续推进，参见 **principle-never-block-on-the-human** 原则技能。预计耗时数小时的工作至少安排一个检查点。

## 阶段 B 设计工作流程

拆成原子且可以独立落地的工作单元。优先消除风险最高的未知项。先做基础设施和验证，再做功能，参见 **principle-foundational-thinking** 原则技能。

- 正式改动前搭建验证工具链并采集改动前基线，使验证能直接比较旧值和新值。
- 不可逆的设计决定用 **architect**，由它驱动 **arena**。结构已经明确的机械性工作可跳过。设计已定时再开一次 **arena** 是过度设计，参见 **principle-laziness-protocol** 原则技能。
- 决定哪些部分可分发。沿清晰的边界并行。每个执行者各用自己的工作树或分支，参见 **principle-separate-before-serializing-shared-state** 原则技能。控制并行数量。按 **poteto-mode** 的「子代理」一节读取角色模型规则并选择档位。使用 `invoke_subagent` 时，未配置角色规则且未显式指定档位默认传 `Model: "inherit"`，已配置或显式指定时按配置传 `"inherit"|"pro"|"flash"|"flash_lite"`；有授权且需要隔离写入时用 `Workspace: "branch"`。外部执行者经 `run_command` 按项目级 `.agents/rules/pstack-models.md` 或用户级 `~/.gemini/config/rules/pstack-models.md` 的规则派发，保持同样的隔离边界。
- 写下设计出的阶段清单。用户据此审阅。

随后执行方案。把具体步骤作为待办项插在阶段 C 与阶段 D 条目之间。每一步按阶段 C 的实验要求执行，落地时就在阶段 D 的记录中填一行。

## 阶段 C 循环检验

每个单元都是一次实验。提出假设，做最小改动，用真实产物核对判定条件。有进展就保留，无进展就撤销。应用 **principle-sequence-verifiable-units** 原则技能，逐个验证，在下一个单元开始前完成当前单元的检查。

- 直接查验产物。执行者自述不能替代检查。过于轻易通过时，先排查观察方法。
- 委派工作配一名评审者。执行者钻了验收关卡的空子时，重置结果并加强任务约定。如果关卡本身有错，单独修正关卡。
- 结论使用 `VERIFIED`（已验证）、`NOT VERIFIED`（未验证）或 `INCONCLUSIVE`（证据不足）。只有「已验证」算通过，如实记下负面结果。

## 阶段 D 保留审计记录

用 **show-me-your-work** 技能记录过程。此类工作通常值得把记录随改动提交，让评审者在 PR 中读取，前提是当前项目允许提交和开 PR。决策记录和 diff 一起交付，方便用户回来核对。

## 阶段 E 验证并交付

用真实产品对照阶段 A 的完成条件验证整体，验证工具链本身通过还不够。把一再出现的纠正落实成验收关卡、lint 规则、检查或脚本，参见 **principle-encode-lessons-in-structure** 原则技能。

**回复**给出设计的流程、严谨程度及理由、决策记录路径、已按完成条件验证的内容，以及仍未解决的事项。
