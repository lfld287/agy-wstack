# 影响范围

在交付前找出改动会影响哪些其他地方。适用于「X 的影响范围多大」「这可能改坏什么」，以及评审让人不放心的小改动。

与 `how`、`why` 配合使用。`how` 说明代码怎样运行，`why` 解释设计成这样的原因，本技能追踪改动会在哪里引发故障。

用 `run_command` 跑 `rg` 眨眼就能列出直接调用方。重点追踪符号搜索看不到的破坏。

## 用运行结果核验判断

单看文字是否可信，无法判断影响分析是真是假。找出整份判断依赖的一两个事实，运行代码证实它们，再给结论和证据。

### 证据有多强

对改动安全所依赖的每个事实，尽量用低成本达到更高一级，并明确做到哪一级。

1. 你说它成立。单靠口头判断没有证明力。
2. 找到具体代码行。给真实的 `file:line`，或者库的源码。
3. 证明故障路径走不通。逐步走完出错所需的链路，指出它在哪一步无法继续。
4. 运行验证。用脚本或测试调用真实代码。如果判断错了，让检查明确失败。
5. 在运行中的应用里复现。

第 4 级通常只需一个小脚本，导入应用实际随包交付的同一版本的库，调用担心出问题的那个函数。

## 步骤

1. **读改动。** 取到 PR 和相关提交，读 diff、增删改的符号及行为差异，包括 diff 未直接写明的变化。
2. **找出决定安全性的事实。** 多数看似有风险的改动，都有一个使其安全的事实，例如「这个调用只丢弃已经失效的缓存条目，不产生其他副作用」。只要它成立，大部分风险场景就能排除。优先花时间验证这一点。
3. **追踪搜索覆盖不到的地方。** 用 `read_file` 读所调用库的源码，核对锁定版本和本地补丁。查清运行时机，包括微任务、卸载与清理，以及 Solid 和 React 各自的行为。沿着符号搜索漏掉的路径追踪，例如 API 返回的 JSON、数据库列、线上传输格式、读取同一字节序列的其他语言、功能开关，以及间隔三层调用的下游代码。
4. **如实评价风险。** 分别给出实际发生的可能性和发生后的代价。保留已证实的风险，另列已排除的场景。给出真实的 `file:line`。搜索无匹配也可作为结果。禁止凭空编造调用方或 API。
5. **实测关键事实。** 写脚本或测试调用真实代码，通过 `run_command` 执行并附上实际结果。
6. **范围大或涉及面广时，运行 [`arena`](../arena/SKILL.md)。** 按 [双引擎调度](../../docs/harness/antigravity.md#双引擎调度) 应用 `~/.gemini/config/rules/pstack-models.md` 和 `.agents/rules/pstack-models.md` 的模型配置。先通过 `run_command` 设置 `WaitMsBeforeAsync: 500`，用 `scripts/multi-model-dispatch.sh --mode readonly` 启动配置中的 `codex` 或 `pi` 后台评审，再用 `invoke_subagent` 发起 AGY 原生批次，按任务选 `Model: "inherit"|"pro"|"flash"|"flash_lite"`。原生评审用 `Workspace: "share"` 并限定只读。用 `manage_task` 核对外部任务结果。向各模型提供相同的 diff、基线与问题，让它们独立判断。不同模型会发现不同的真实缺陷，逐项核查证据后再汇总。

## 交付内容

- **改动做了什么。** 包括 diff 上不明显的行为变化。
- **决定改动安全性的事实。** 陈述事实、达到的证据级别以及证明。无法证实就标为「未证实」。
- **风险。** 每项写清触发过程、`file:line`、发生可能性、后果和核对方法。对重要风险附上证明。
- **已排除项。** 写清检查了什么及排除依据。
- **合并前检查。** 给出抓住实际缺陷的最低成本测试或复现方法，附上已写的脚本。

用 `unslop` 打磨文字，引用真实代码。对外公开前先去掉私密内容。

**回复**按上述结构给出分析，将安全性依赖的事实标为「已证实」或「未证实」。
