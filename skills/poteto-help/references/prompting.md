# 写提示词

提示词说明意图和完成检查。步骤交给 playbook，几句平实的话就够。

## 写进去的内容

- 目标。说明哪里出了问题，或用户想要什么。
- 完成检查。它必须可判定通过或失败。「做得更好」和时长都无法作为检查。
- 要展示的证据。可以是真实命令的输出、流程录像、存储值或前后对比数据。
- 用户已经掌握的事实。症状、复现步骤、日志或链接都能省下一轮搜索。
- 实际约束。「先复现」「先别改代码」「行为零变化」「让我审完再继续」都会改变代理的做法。

## 可以省掉的内容

- 实现方案。说清要实现什么，让代理有机会找到更好的做法。
- 技能或步骤清单。手写顺序容易漏掉或调换 playbook 原有的步骤。只在需要改掉某项默认选择时点名技能。
- 对成因的猜测。在代理复述问题后再说。过早给出猜测会缩小它的搜索范围。

## 先加载上下文

- 对线索杂乱的报告，要求代理动手前先用自己的话讲清根本问题。这样可以在写任何代码前发现误解。
- 新聊天用 `/recall` 回顾该主题以前的工作。旧聊天里有新代理缺失的上下文。
- 改陌生代码前，用 `/how` 了解机制，用 `/why` 了解原因。没有追踪过运行过程的代理，往往会在第一个看起来合理的位置修补症状。
- 用 `/teach` 要求代理给某项选择举证，例如「说服我，你修到了根因」。有论证的说法比摘要容易核查。

## 先设计，再规划

- 先要几个方案的原型，再从证据里挑。界面原型附截图或视频。别直接采用第一种设计。
- 让原型回答悬而未决的问题。对抽象计划做对抗审查，常会产生根本不会发生的假设风险。
- 对共享包或 API，先要 README 或教程，再反推代码。文档会成为代理检查自己的目标。
- 设计确定之后再要计划。计划每一步都以一项检查收尾。

## 简短跟进

- 聊天已有完整上下文时，「做吧」「继续」「做到完成」都是完整提示词。
- 换主题时以 “new task” 开头，否则模式会把消息当成原任务的下一步。

## 离开前

- 说 “im going to bed” 或 “im stepping away”，让代理继续，无须等待日常决定。
- 把完成条件写成每轮可运行的检查，并把这个判定条件交给 `schedule`。
- 要求从指定基线开一个新 worktree。
- 预先回答代理会停下来问的授权问题，例如「提交前不用问我」。
- 要求保留决策日志，方便回来审计。
- 写明退出条件，例如「几小时后如果确实卡死，停下并写清原因」。

## 一句话纠偏

- 重申目标。「我的目标是复现。暂时没有要求修复。」
- 点名原则。「应用 prove it works。给我实际运行的输出，构建日志不够。」
- 点名有效，是因为代理已经读过规则。它的回复会指出该原则改变了哪个决定。
