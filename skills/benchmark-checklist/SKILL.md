# 基准测试检查清单

只要要给出性能数字，就用这份清单。适用于 PR 的前后对比、性能回退判断、Hillclimb 测试工具链，以及库或配置的选型。每题都用实测证据作答。

用户只想要一个粗略量级时，跑一次即可。仍需核对第 4 和第 7 题，并说明只跑了一次。单次结果看起来异常时再查其余各题。方案选型必须完整验证。

## 开跑前

- 用可直接对外报告的措辞写下预计得出的结论，例如「在 6 万行的数据集上，导出在 p50 下提速 30%」。以下问题都用来检验这句话。
- 用 `read_file` 阅读测量脚本，记录它计时、计数和忽略的内容。
- 用 `run_command` 执行 `uptime` 查平均负载，用 `nproc` 查核心数。macOS 没装 `nproc` 时，可用 `sysctl -n hw.logicalcpu`。机器繁忙时查明正在运行什么。无法停掉干扰任务时，交替跑各组，让各组经历同样的噪声，并在报告中说明。

## 七个问题

1. **为什么没有快一倍？** 找出瓶颈。另跑一轮采集剖析数据，报告用无剖析的测量数据，因为分析器和追踪器会拖慢程序。查看各进程的 CPU 用量（`top`、`pidstat`）、运行时剖析结果（`node --cpu-prof`、`py-spy`、`perf`）、I/O 等待和系统调用次数（Linux 上用 `strace -c`），再把热点定位到源码。同时监看负载生成器。它若先饱和，测到的是负载生成器的上限。如果改动没让数字变化，先找出瓶颈，再评价改动有没有用。
2. **各组都按实际用法调优了吗？** 每组都按生产方式运行，用发布构建、生产环境变量和参数、批处理与事务设置、连接池，以及与生产实际一致的冷热缓存状态。使用相同的版本和数据。哪一组用了默认设置，这轮比较的就是配置。瓶颈若来自一个设置，例如每行提交一次、调试构建或缺少索引，就先调优、重测，再选赢家。如果无法调优，这轮无法定胜负。用户在决定采用哪个方案时，将结论限定为目前出厂设置也解决不了这个问题，因为用户会采用整个方案，设置可以调整。
3. **结果超过理论上限了吗？** 算一遍。将每秒字节量与磁盘和网络带宽比较，将每秒操作数乘以单次成本后与核心数比较，再把节省的时间和被改部分原本的耗时对比。移除一个占总耗时 10% 的环节，整体最多约快 11%。结果越界时，测到的可能是缓存、空操作或程序错误。
4. **有错误吗？** 统计失败和非成功响应，检查输出内容确实正确。拒绝请求通常很快，超时和重试通常很慢。脚本没数错误就补上计数。
5. **能重复测出来吗？** 每组至少跑 5 次，按 A、B、A、B 的次序交替，避免预热、延迟初始化、缓存和时间漂移偏向某一组。报告中位数和范围。两组差距小于轮次间波动时，结论是「未测出差异」。两组接近时，用秩和检验或工具链自带的统计方法。
6. **对用户有影响吗？** 每个微基准结果都要同时测量用户实际等待的端到端路径，用真实的典型数据规模和并发度，并报告微基准所测部分占全程的比例。某个辅助函数只占请求耗时的 1% 时，即使它开销降到零，请求也最多快约 1%。
7. **工作真的执行了吗？** 确认工作发生在计时区间内。请求确实到达服务端，行确实写入，字节确实读出，程序也确实用到了结果。没有被迭代的生成器、没有被等待的 Promise、可被 JIT 消去的结果，以及超时，都可能让脚本为实际没有完成的工作报出数字。

## 报告

- 先给结论。更快、更慢、未测出差异，或证据不足。
- 给出带单位的数字、运行次数、范围和瓶颈。例如「p50 从 41 ms 降至 33 ms，两组各跑 7 次取中位数，改动后范围 32 至 35 ms，受单核 JSON 解析限制。」
- 声称存在差异却找不到瓶颈、有一组没调优，或第 4、7 题无法核对时，结论为证据不足。具体写出缺口。
- PR 正文只放一个主要数字。各次结果、范围和瓶颈证据放在链接所指的产物或记录文件里。

## 其他性能流程

- **Perf issue** 流程拿基线来定计划之前，先用本清单核验基线，之后的每个数字也要核验。
- **Hillclimb** 流程锁定测量工具链前先核验它。锁定后让它打印错误计数和实际工作量，这样每次判断保留或回退时都自动验证第 4 和第 7 题。
