# Arena

启动前建立待办，逐项跟踪定题、并发、交叉评审、选底稿、整合、验证。

## A. 定题

1. 明确每位候选要交付的同一个产物。给所有候选相同任务、基线、共享资料路径和交付规格。
2. 从本次意图提炼 3 至 6 条可逐项评分的标准，留给父会话和交叉评审。候选收到任务，不接收内部评分表。
3. 按 [双引擎调度](../../docs/harness/antigravity.md#双引擎调度) 读取 `arena runners`。缺失时以 `agy:pro, agy:flash` 起步，可加入确认可用的外部模型。每项一个候选，含 `agy:inherit`。优先让 AGY 和已确认的外部引擎同轮运行。只有生成量是瓶颈时才重复同一模型。若模型被拒绝，优先选择同家族已确认可用的对应项，再用可用原生级别，必要时退席并说明。保留至少两位。人数不足时报告比选未完成。
4. 识别家族时先从模型 ID 剥离供应商前缀和推理后缀，按最具体的前缀匹配。Fable 与其它 Claude 可属不同家族，供应商同为 Anthropic。区分家族、供应商和执行引擎。
5. 每位候选使用独立写入位置。Git 工作区可准备独立工作树，AGY 可用 `Workspace: branch` 或 `share`。非 Git 任务给每席独立目录，例如 `/tmp/arena-<run>/candidate-<n>/`。需要修改同一初始文件时，先为各席准备同一基线的独立副本。

## B. 并发生成

每个简报首行要求读取绝对路径的 `worker.md`，随后写明任务、共享资料、该席工作区和产物路径。要求提交可审阅产物和短说明，列明考虑过的替代方案及排除理由。

在同一父会话轮次先为每个 `codex:` 或 `pi:` 席调用 `run_command`，设置 `WaitMsBeforeAsync: 500`。执行 `scripts/multi-model-dispatch.sh` 的绝对路径，传 `--engine`、`--model`、`--cwd`、所需的 `--mode`、该席的 `--output` 及 `--prompt-file`。随后在同一轮为每个 `agy:*` 席单独调用 `invoke_subagent`，传顶层字段 `TypeName`、`Role`、`Prompt`、`Model`、`Workspace`。启动完这一轮再汇总，通过 `manage_task` 管理外部任务，按 ID 确认退出和产物。缺少产物的候选退席并记录。

## C. 交叉评审

候选齐备后从 `arena cross-judge pool` 依序选出一位只读评审。未配置时，用已确认的其他供应商模型作为候选。跳过 `agy:inherit` 与父会话同供应商的项。父模型未知时可用首个实际可用项，但须写明供应商未核实。模型被拒绝时尝试同家族合法项，再试下一候选。无合适人选时记录跳过。

只读评审可走任一引擎。用可用的原生只读审查类型或外部脚本的 `--mode readonly`，给出编号的候选与评分表。要求逐项打分并推荐底稿。父会话独立阅读和打分。

## D. 选底稿

完整读每个候选并逐项核对标准。交叉评审完成后对比分数。若选择不同，重读双方理由，判断是标准含糊还是取舍不同。优先选未来维护者容易扩展且能维护不变量的产物。难分高下时看谁的边界更清楚、API 更小。

## E. 整合

逐一复查其余候选，通常每项只取一两处有效做法。将它们融入底稿的结构，按 `principle-redesign-from-first-principles` 保持设计一致。候选收敛时交付共同方案。候选分歧大到无法比较时补全任务说明和标准后重跑。

## F. 验证

按 `principle-prove-it-works` 验证整合后的真实产物。遇到新问题时检查定题是否缺条件，或某候选已提出可用修正。回到对应阶段处理并复验。

## 交付

交付一份综合产物和短说明。记录底稿、选择依据、交叉评审的结论或跳过原因、采纳片段及来源、拒绝项、收敛情况、退席和实际验证结果。
