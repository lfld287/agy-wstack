# 把我的工作方式写成技能

按以下流程把用户的工作约定整理成代理能遵循的技能。交付一个为该用户定制的 `-mode` 技能，例如 `jay-mode` 或 `priya-mode`。

本技能依次组织三项工作。先按第 1 步在本流程内挖掘会话证据，再用环境中的技能编写技能起草，最后用 **unslop** 约束措辞。各项工作仍按各自的方法执行。

在 AGY 中使用已安装的 `create-skill` 或 `skill-creator`。两者都没有时，遵循 agentskills.io 的 Agent Skills 格式。下文用 `create-skill` 指代实际采用的编写技能或规范。

## 流程

### 0. 检查已有技能

在项目级 `.agents/skills/` 和用户级 `~/.gemini/config/skills/` 内，用 `run_command` 配合 `rg --files` 或 `find` 递归搜索和用户标识匹配的 `*-mode/SKILL.md`。也要检查 `<skills>/<handle>/` 这样的个人分类目录。若已有技能，用 `ask_question` 确认意图。用户已明确说「更新我的技能」等同等指令时，直接进入更新模式。

- 更新已有技能。重复运行时默认选这项。
- 从头创建。这种情况较少见，动手前询问原因。

更新模式对后续流程有三处影响。

- 第 1 步只挖掘上次编辑以来的历史。Git 项目用 `git log -1 --format=%cI <path>` 找到最近一次修改该技能的提交时间。没有 Git 历史时，使用可确认的编辑时间或文件修改时间，并说明依据。
- 第 2 步询问哪些约定变了、还缺什么。
- 第 4 步用 `edit_file` 原地更新。保留用户未否定的章节，根据新证据修订现有条目。只有真正新增的规则才需要新章节。

### 1. 挖掘会话历史

派发任务前，先确认哪些 AGY 会话属于当前工作区。使用当前会话 ID，以及用户提供或可信工作区元数据已确认归属的历史会话 ID。只打开这些 ID 对应的目录。把同一工作区的前提查清后再读正文，禁止对整个 `brain/` 做通配或搜索，以免把其他项目的私密对话读进来。

- 摘要记录在 `~/.gemini/antigravity-cli/brain/<conversation-id>/.system_generated/logs/transcript.jsonl`。
- 完整记录在同目录的 `transcript_full.jsonl`。优先读摘要，只有证据所在记录缺失或有 `truncated_fields` 时，才按 `step_index` 去完整记录核对。

用 `read_file` 定点查看，或用 `run_command` 逐行解析 JSONL。下例中的 `<conversation-id>` 只替换为已确认的 ID。

```sh
log_dir="$HOME/.gemini/antigravity-cli/brain/<conversation-id>/.system_generated/logs"
jq -c 'select((.type == "USER_INPUT" and .source == "USER_EXPLICIT") or .type == "PLANNER_RESPONSE") | {step_index,created_at,type,source,content,tool_calls,truncated_fields}' "$log_dir/transcript.jsonl"
```

以 `type: USER_INPUT` 且 `source: USER_EXPLICIT` 的条目识别用户原话，用相邻的代理回复、工具调用及结果核对上下文。以 `created_at` 筛选时间窗，引用时保留会话 ID 和 `step_index`。

在这个范围内查找近期会话里反复出现的模式。把历史分片，由多个 `invoke_subagent` 并行挖掘，例如把最近 2–4 周分成 3 片，让每片都有足够材料。按 **poteto-mode** 的「子代理」一节为任务选择适当的推理级别，并映射为 AGY 的 `Model: "inherit"|"pro"|"flash"|"flash_lite"`。只读子代理可用 `Workspace: "share"`，每个只读主代理传入的已确认日志路径和时间片。要求各自返回简短的结构化模式清单与证据位置。默认查找以下信号。

- 回复偏好，例如篇幅、语气、格式，以及「说简单点」一类纠正。
- 委派习惯，例如子代理、模型、专用流程和并行安排。
- 验证要求，例如什么才算完成、何时要单元测试或真实复现、何时让评审者介入。
- 代码和文字规范，例如风格、常引用的原则、lint 和格式化工具。
- 流程约定，例如工作树、提交、PR、评审和合并工具。
- 技能维护偏好，例如任务进行到一半时修技能、何时提议新技能。

将信号提升为规则前，先跨时间片核对。至少两片都出现的模式可信度较高。仅出现一次的信号证据较弱，通常舍弃。

### 2. 直接询问用户

有些意图从未在会话中出现。用 `ask_question` 给出结构化选项，减少用户从头描述的负担。工具不可用时，在对话中给带编号的选项。

设置一到两道结构化题，每题四到六项。类别题使用多选，前提是当前工具支持多选。先问「你最在意哪些方面」这样的宽问题，再就用户选中的方面给具体选项。结构化问答结束后，再用一个开放问题补齐选项之外的内容。

别一下抛出二十个问题。

### 3. 整理发现

把会话证据与用户回答归成章节，按需选用以下类别。

- **回复风格**。篇幅、语气、格式。
- **自主程度**。哪些事可直接做，何时询问，以及 MCP 工具的使用。
- **先理解再动手**。界定或调查改动时先用哪些技能。
- **子代理**。默认用法、并行策略、任务与模型的匹配、专用流程。
- **文字和代码规范**。采用的原则、lint 工具和风格指南。
- **评审和验证**。何时复现、使用哪些验证技能和运行态测试工具。
- **流程**。Git 工作树、提交、PR、评审及合并工具。
- **技能**。编写习惯、先修技能的时机、何时提议新技能。

阅读 **poteto-mode**，参考它的组织方式和颗粒度。新技能的内容来自当前用户的约定。

### 4. 起草技能

按 `create-skill` 的规则编写，使用 `write_file` 创建或 `edit_file` 更新指定的文件。

- **位置**。已有模式沿用原分类。新模式如果所在仓库有个人分类惯例，用 `<skills>/<handle>/<handle>-mode/SKILL.md`。否则放在项目的 `.agents/skills/<handle>-mode/SKILL.md`，用户偏好全局使用时放在 `~/.gemini/config/skills/<handle>-mode/SKILL.md`。
- **标识**。用用户的名字或其自选标识。
- **Frontmatter 的 `description`**。以用户名字、`/<handle>-mode` 和「按这个人的风格工作」触发。避免「写代码」「评审 PR」之类过于宽泛的触发词。
- **Frontmatter 格式**。遵循 `create-skill` 的 YAML 规则。`description` 保持为一个标量。标点或换行需要时，加引号或用带缩进续行的 `description: >-`。
- **调用方式**。默认设 `disable-model-invocation: true`。用户明确希望每轮都应用个人模式时才取消。

### 5. 打磨文字

逐行应用 **unslop** 和 `create-skill` 的写作规则。把草稿给用户看，吸收反馈，预期会修改数轮。大胆删掉无关内容，把模式技能控制在约定所需的篇幅。

### 6. 交付

项目使用 Git 且有相应授权时，从主分支创建工作树，在其中提交并开 PR。禁止直接推送主分支。非 Git 项目或仅授权本地写入时，在约定位置交付技能文件。

## 约束

- **避免过拟合单次对话**。一处提到、另一处又被推翻的偏好不作为依据。有多次证据再写成规则。
- **写得能执行**。避免重述其他技能、自造比喻或追求辞藻。
- **引用依赖**。用户依赖的其他技能和自行维护的原则文档以路径引用，正文留在原文件。
- **只保留承载具体约定的章节**。「清楚沟通」过于泛化。「段落简短。比较选项时用表格。只有各项确实并列时才用项目符号。」才是可执行的约定。
- **规则使用通用称呼**。祈使句中称「用户」或「操作人」，用用户名字触发技能即可。
- **按需组织章节**。用户没有值得记录的流程规则，就省去整个流程章节。

## 评估

`-mode` 技能依赖用户的主观判断。请用户确认是不是他们的做事方式、有没有漏项，确认后交付。把 `create-skill` 式的基准测试与迭代留给客观可测的任务。

只有实际使用中出现触发不准，才迭代优化描述。

## 何时使用其他技能

- 需要特定任务技能时，直接用 `create-skill`，无需挖掘历史。
- 只记录一个具体流程，例如「我怎么写提交信息」，用普通技能即可。
