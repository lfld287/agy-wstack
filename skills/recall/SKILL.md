# 回顾工作

**开始或恢复工作前，复原用户近期的工作上下文，并用一份简短摘要说明当前状态和下一步。**

紧扣主题。只读范围内各条工作线所需的材料，读够就停。

上下文来自两类记录。自身聊天历史记下你做过的事和决定。共享记录存着围绕同一段代码、以其他名目留下的材料，包括用户反复报告的症状、上线后被撤回的修复、生产环境仍在触发的错误。第二类记录分布在版本控制、问题跟踪器、聊天和问题频道、长篇文档和错误跟踪系统里。积累了大量后续缺陷的功能，其来龙去脉大多在共享记录里。重建时同时查阅这些来源。

AGY 会话记录采用 JSONL，位于 `~/.gemini/antigravity-cli/brain/<conversation-id>/.system_generated/logs/transcript.jsonl`。查找时先确认会话属于当前工作区。如果需要识别其他环境中已有的记录，可用下列路径定位。

- **Cursor。** `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`。`<slug>` 来自工作区路径，去掉起始斜杠，再把每个 `/` 换成 `-`（`/Users/you/proj` 变成 `Users-you-proj`）。
- **Claude Code。** `~/.claude/projects/<slug>/<session-id>.jsonl`。`<slug>` 来自工作区路径，每个非字母数字字符都换成 `-`（`/Users/you/proj` 变成 `-Users-you-proj`）。
- **Pi。** `~/.pi/agent/sessions/--<slug>--/<timestamp>_<id>.jsonl`。`<slug>` 来自工作区路径，去掉起始斜杠，再把每个 `/` 换成 `-`（目录为 `--Users-you-proj--`）。
- **Codex。** `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`，按日期存放。仅选第一行的 `payload.cwd` 等于工作区路径的文件。
- **OpenCode。** `~/.local/share/opencode/storage/`。会话 JSON 在 `session/<project-id>/`，消息在 `message/` 和 `part/`。

1. 先分类，再选择流程。接续某个特定的旧会话用 `session-pickup`。把操作习惯固化为长期技能用 `automate-me`。供人阅读的工作总结另行处理。回顾工作的用途是在动手前从近期多次聊天中载入工作上下文。用户若已给出完整状态摘要（路径、分支、变更），直接使用。
2. 搜索前锁定范围。确定时间窗口（「近期」默认过去 7 天）、用户点名的主题和工作区（默认当前工作区。未经要求，禁止读取其他项目的会话）。向用户复述范围。遇到「全部」按全部处理。
3. 并行查聊天历史。用 `invoke_subagent` 启动快速、低成本的子代理，各查一段记录。要求每个子代理按实际修改时间排列候选（`ls -t`），避免按 UUID 排序。先 grep 主题，只读匹配会话的相关段落，跳过当前会话和明显噪声（子代理、评估和测试会话）。每个子代理用同一结构，每次会话一块，列出主题、用户目标、决定、未解决事项、遇到的困难和纠正，以及产物（PR、工单、分支）。各项引用会话 UUID。只有一两次会话时直接搜索即可。原始会话记录留在子代理，主会话只接收调查结果。按 **poteto-mode** 的子代理章节选择推理档位。
4. 主题点到了功能、文件、子系统、领域或缺陷，就同时查共享记录，「我在 X 上的工作」也适用。每种来源用 `invoke_subagent` 启动一个调查代理，为它保留读取所需 MCP 的权限。向每个代理询查「现状如何、试过哪些方法但没能维持、用户仍在报告什么」。这一步与聊天历史调查并行。查不到也是结果。MCP 不可用时，跳过并说明。将结果合入简报。只在纯活动回顾且没有点名目标时跳过这一步，例如「我这周做了什么」，此时自身历史和实时状态已足以回答。
5. 对照实时状态核实。用 `git` 和 `gh` 核对调查发现的 PR、分支和工单。如果结论取决于代理实际做了什么（用了哪些工具、读了哪些文件、碰到什么错误），读完整记录，避免只看截短的本地副本。
6. 按下文的约定写简报。以工作线分组，并紧扣指定主题。

## 输出约定

依次写摘要、各工作线状态、问题和下一步。更深的细节放在后面，必要时删减。

- **摘要。** 最多 5 条。说明这项工作是什么，整体进展如何。
- **工作线。** 每条一行，行首仅加一个状态标签。`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。每条都必须标记，漏标就没写完。
- **问题。** 最多 5 条，列出反复出现的问题。写明用户持续反馈的症状，以及上线后撤回的修复，让下一次接着上次失败处做。
- **下一步。** 给出当前最有用的一项具体行动。

相邻功能或工单只在它阻塞本项工作时纳入。摘要和工作线加起来超过一屏时，先压缩细节，保住各条工作线。用 **unslop** 整理简报，以 UUID 引用聊天发现，以来源标明共享记录的发现（PR 编号、工单 ID、聊天永久链接、错误跟踪条目），向外公开前去除私密内容。

**回复。** 只交按上述约定写成的简报。
