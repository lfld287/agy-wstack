# 讲解

**按对方跟得上的节奏，用一份平实的说明讲清对象是什么、怎么运作、为什么这样设计。目标是让对方理解。**

本技能以 `how` 和 `why` 为基础。先弄清这项工作及其涉及的内容，再运行 `how` 查机制，运行 `why` 查原因。这两个技能要实际调用，由它们各自调查。把发现合成一份平实的解释，先说对方最在意的，再按提问深入。讲解时可以自由改写，唯独要原样保留 `why` 表达置信度的措辞。它的保留意见也是调查发现。

1. 决定对方听完应理解哪几件事。从对话判断他们为什么问（准备修改、正在审阅、在排障或初次接触）以及他们已经知道什么。根据已有信息判断，省去测问。跳过对方显然已知的部分，把篇幅留给他们真正问的地方。
2. 让 `how` 和 `why` 做各自的调查。自己读代码以了解全局，再分别调用 `how` 查运作方式和 `why` 查成因。用 `invoke_subagent` 并行时，给两边各自的技能和调查目标，再合并结果。按问题大小决定用量。一个子系统通常两项都跑，小改动可能一项就够。
3. 先给直白的定义。点明对象，用资深工程师日常交流的方式介绍它一般是什么，有通用名称就用通用名称。再联系眼前的案例，例如「在 X 中，我们用它来……」，逐步讲到机制、更深的原因和边界条件。每一部分都要说清它解决什么问题、具体如何实现。有助理解时，沿着对方实际做的事讲一遍，例如打开长聊天、向上滚动时发生了什么。函数和常量清单适合作为参考资料。省去「只要记住这一点」「重点摘要」「核心洞见」「从根本上说」「TL;DR」等套话。先用一两句给出最小的完整回答，避免压成密集的一大段，然后停下来。对方追问时再深入。避免整墙文字。
4. 保持对话，不讲长课，也不表演教学。可以提供进一步展开或转到下一段的选择，再按对方的节奏继续。省去测验和刻意安排的节拍。别打印「暂停」，别要求对方复述，也别预告「一定要记住的那句话」，或用「这里值得放慢」「这是难点」「这里开始有趣」标记段落。直接讲内容。该停时停下来等对方回应。一次性回答、没有实时对话对象时，完整交付内容，如需提供进一步展开的选项，放到末尾。
5. 能展示就展示，用一组图逐步建立认识。打开 diff、代码或调试器能更快说明问题时，就用它。画图比文字清楚时就画图。涉及至少三个活动部件时，画成一个短序列，每张重画上一张，只添一个部件，让读者看着系统组装起来。一张事物齐全的总图适合查阅，尤其是放在最后时。例如，要讲 A 到 B 再到 C 的流程，就画三张。先画 A 到 B，再重画并加 C，最后重画并加返回边或下一项。按内容选媒介，两种都有用时可以并用。标签承载意义的流程和结构适合 Mermaid。布局、重叠、滚动位置或前后对比等空间问题，适合用图像生成工具画白板马克笔风格的图，配少量短标签，因为图像模型容易写乱长文本。实际生成这张图。生成图同样要逐步展开。单一而简单的点可以省图。

每次回答都经过 **unslop**，用给同事讲解时的口吻，平实、紧凑，保留能让对方听懂的内容。删掉填充语和无谓的缓和措辞。直接说明机制，省去比喻、框架话和预告。目标密度例如「虚拟化分为渲染和从磁盘加载两部分。条目滚出缓冲区后，其 DOM 节点和内存数据都会移除。」英文用正常的句子大小写。避免破折号。优先用句号，每句最多一两个逗号。分句堆起来就拆句。每个概念只用一个固定名字。避免「没有 B 的 A，或没有 A 的 B」的镜像句式和「其余的顺势而来」「剩下的就自然清楚了」之类整齐套语。上面的步骤是操作指引，标题和套话无需沿用其结构。

**回复。** 直接给解释。先讲主要结论，再平实说明它是什么、怎样工作、为什么这么设计，以及有哪些线索值得继续用 `how` 或 `why` 追查。
