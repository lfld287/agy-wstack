# 创建形式化验证技能

测试检查编写者想到的用例。形式化验证穷尽声明范围内的情况，例如模型里步骤的每种顺序、指定界限内的所有输入，或所有输入。本技能找出仓库里最需要这种验证的代码，验证它的一项性质，再留下一个项目技能，让下一位代理检验改动是否仍满足该性质。假定接手者在改代码的途中首次打开技能，从未见过你的工作。用户应能相信结果并据此行动，无需学习验证语言。

## 从代码中选择目标

从仓库找答案，只有观察不到的信息才问用户。用户已经点名某个区域或缺陷时，从那里开始。

好的目标是代码对用户作出的承诺。一旦违背，用户会受损，而测试很少触及违约场景。选仓库里最符合这些条件的目标，即使验证起来更费力。

## 按问题选择工具

选能以最低成本回答问题的工具，例如模型检查器、证明助手、由 SMT 求解器支持的验证器，或其他合适工具。要检查事件是否可能按错误的顺序发生，通常用小型设计模型做模型检查，不论产品代码用什么语言，默认选择 TLA+。要检查实际代码对每个输入的行为，例如内存安全、溢出或数据结构不变量，通常用直接作用于代码的验证器。若该语言没有可用验证器，说明这一点，用生成的输入测试真实代码，避免只验证手写的函数模型。性质必须在任意规模下成立时，有界验证可能不够，需要给出证明。优先选择项目开发者能安装和运行的工具，并告诉用户选择理由。

## 质量要求

- **贴合代码。** 模型或证明的每一部分都指向评审者能打开的源码。在验证中视为原子步骤的行为，在代码中也必须是原子的。用仓库里的实际命名。
- **能够失败。** 亲眼看到每项性质在被破坏的代码变体上验证失败，例如删掉一个检查，或调换两个步骤。
- **如实报告发现。** 当前代码违反性质时，用代码里的概念描述反例并报告。禁止放宽性质或模型来求通过。只有用户要求时才改产品代码。
- **说明范围。** 交代验证了什么、采用的界限和假设、哪些内容未覆盖。通过仅针对所用模型或限定范围。
- **无需懂工具也能看懂。** 分别用一句通俗的话写清性质和危害。反例用代码里的术语讲成一段简短的操作序列。
- **易于重跑。** 给出一条命令和可复现的工具版本，让运行时间短到接手者愿意在每次相关改动时执行。AGY 中通过 `run_command` 运行。
- **与代码同步。** 记录每项检查覆盖的文件和函数，以及上次确认验证仍能描述这些代码的提交。覆盖的代码在此提交之后变动时，接手者能看出需要重新核对。

## 生成验证技能

用 `write_file` 将项目级技能写到 `.agents/skills/<技能名>/SKILL.md`，在 frontmatter 写清覆盖区域和使用时机。技能注册依赖 frontmatter。仅凭这个文件，下一位代理就应能判断改动是否涉及已验证代码、运行检查、区分真实缺陷和建模错误，并在行为有意变更时更新验证。把覆盖记录和同步提交写进技能，提示接手者只有确认验证能描述新提交上的代码后，才前移同步提交。使用本仓库的真实命令、路径和术语，确保没有占位符。

使用 TLA+ 模型时，要求接手者用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能解读每次结果。它将检查器发现的每个不变量违规用通俗的话呈现为一条最短路径。检查通过时，`/statechart` 会画出系统如何在状态之间迁移。按技能名引用 `/statechart` 即可。它的命令、选项和文件路径随版本及机器而变，禁止复制进生成的技能或脚本。

## 交付前实际验证

像接手者一样完整执行一次生成的技能。临时改动真实代码使其违反性质，确认检查能抓住问题。再撤销临时改动，确认恢复到原来的检查结果，即通过或仅因即将报告的发现而失败。未运行过的验证技能仍是草稿。如果检查漏掉故障，或有步骤跑不通，修正技能或验证本身，以同一处临时故障重新检验。

## 交付

向用户说明验证了什么、所用工具及理由、验证界限、检查发现、运行方法和未覆盖的内容。用通俗语言描述发现。只有发现了优先级相近的另一个目标，才建议接下来验证它。若后续改动绕过了重检流程，使用 `/maintain-formal-verification-skill` 让验证重新与代码同步。
