# 用 TDD 修复缺陷

如果缺陷有明确、低成本的测试途径，先用可执行检查复现错误行为，再改生产代码。目标是一项聚焦的回归测试，修复前失败，修复后通过。

测试不切实际时，选最接近且有用的验证方式。如果可用的测试要大范围搭建测试环境、用脆弱的 mock、依赖缓慢的端到端基础设施或仅生产环境才有的状态，或者复现步骤模糊、需要大改无关 fixture，就跳过新增测试。

## 工作流程

1. **理解缺陷。** 确认预期行为、当前行为、受影响路径，以及能观察到问题的最小复现。
2. **选择最小的可执行检查。** 优先采用该代码路径已有的、最贴近问题的单元测试、组件测试、集成测试或回归测试。如果没有明显可行的测试途径，别只为满足流程从零搭一套。
3. **先写失败测试。** 添加最小且聚焦的测试，确保它本可以捕获这个缺陷。测试表达预期行为，避免照抄当前实现。
4. **修复前运行新测试。** 确认它因预期原因失败。如果测试通过或因无关原因失败，先纠正测试或复现，再编辑实现。
5. **修复缺陷。** 对生产代码做满足预期行为的最小修改，保留周边契约。
6. **重新运行回归测试。** 确认测试现在通过。

## 失败测试不可行时

采用最接近问题的可执行回归检查，例如定向脚本、手动复现命令、浏览器自动化、快照比较、日志断言或聚焦的集成检查。

可以不加测试，避免加坏测试。主要测试 mock、把当前实现细节变成要求、依赖时序或无关全局状态、为小修复引入昂贵的基础设施，或验证修复后马上就会删除，这些测试都不合适。

## 约束

- 禁止为迎合错误实现而改测试。
- 只有预期行为确实改变且理由明确时，才放宽已有断言。
- 让回归测试聚焦缺陷。避免大改 fixture 或扩大无关覆盖。
- 缺陷若时有时无，尽量让测试可确定地复现，并写明它锁定的信号。
- 缺陷若暴露了一整类故障，先完成聚焦的回归验证，再考虑相邻场景的覆盖。

## 最终回复

报告结果和证据。

- 写明修复前失败的测试或可执行检查，以及具体的失败结果。
- 写明修复后通过的测试运行，以及对周边行为所做的验证。
- 如果无法证明修复前失败，说明原因，并描述实际采用的最接近的回归检查。
